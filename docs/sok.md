# Agentic System 在安全研究中的应用与技术贡献

> 对话终稿的仓库副本，正文内容保持不变；仅添加来源提示与导航锚点。[文献目录](../README.md) · [分类映射](mapping.md) · [来源说明](provenance.md)

Agentic System 将大语言模型（Large Language Model, LLM）的推理能力与工具调用、环境交互和执行反馈相结合，使系统能够围绕任务目标获取信息、执行操作，并根据执行结果调整后续行动。近年来，相关技术逐渐应用于漏洞发现、程序测试、漏洞复现和自动化漏洞修复等安全任务。

本文通过梳理近年来安全四大会议的相关研究，重点回答一个问题：**Agentic System 如何解决传统安全技术面临的困难？** 围绕这一问题，我们首先分析不同安全任务的特点及传统方法的局限，再归纳相关工作的关键技术设计，最后讨论其有效性评估方法、技术贡献及后续研究方向。

## 2 传统安全任务及其技术挑战

参考已有 SoK 对安全任务的分类方式，特别是 [SoK: Automated Vulnerability Repair: Methods, Tools, and Assessments（USENIX Security 2025）](https://www.usenix.org/conference/usenixsecurity25/presentation/hu-yiwei) 对漏洞分析、补丁生成和补丁验证的梳理，我们结合所收集论文的研究目标，将相关安全任务归纳为以下七类。本节介绍各类任务的研究目标与技术特点，并分析传统自动化技术面临的主要挑战。

1. **程序安全分析与漏洞检测（Program Analysis and Vulnerability Detection）**

   程序安全分析通过检查源代码或二进制程序，识别潜在的安全缺陷。现有静态分析技术，如污点分析（Taint Analysis）和数据流分析（Data-flow Analysis），通常依赖预定义的漏洞模式或检测规则，能够有效识别符合已知模式的安全缺陷。然而，部分漏洞的判定高度依赖具体应用的业务逻辑。例如，识别访问控制漏洞需要确定用户对特定资源应具有哪些操作权限，而这些要求可能分散在业务代码、配置文件及跨服务调用关系中，难以直接转化为通用检测规则。随着软件系统的功能及组件日益复杂，如何准确识别应用特定的安全要求，并据此开展漏洞检测，成为自动化程序安全分析面临的重要挑战。

2. **动态安全测试（Dynamic Security Testing）**

   动态安全测试通过执行目标程序并观察其运行行为发现安全缺陷，典型技术包括模糊测试（Fuzzing）、符号执行（Symbolic Execution）和黑盒安全扫描。测试效果在很大程度上取决于输入能否通过程序检查，并到达更深层的执行路径。实际软件通常包含复杂的输入约束和状态依赖。例如，文件解析器要求输入满足特定格式及字段间的约束；Web 应用中的部分功能则需要经过身份认证、对象创建等一系列操作才能访问。传统模糊测试容易产生被程序提前拒绝的无效输入，而符号执行也受到路径爆炸和复杂环境建模的限制。此外，代码覆盖率的提升并不意味着一定能够发现更多漏洞，触发特定缺陷往往还需要满足额外的程序条件。因此，复杂输入生成、程序状态准备及漏洞相关路径探索，是动态安全测试中的主要挑战。

3. **漏洞复现与利用验证（Vulnerability Reproduction and Exploit Validation）**

   漏洞复现旨在根据已有漏洞报告或漏洞线索，在受影响的软件中重新触发目标漏洞，并确认其安全影响。这一过程通常需要确定受影响的软件版本及依赖配置，恢复漏洞触发所需的程序状态，并构造满足特定条件的测试输入。然而，公开漏洞报告往往只描述漏洞成因及其潜在影响，缺少完整的环境配置、前置操作或可执行的概念验证程序（Proof of Concept, PoC）。即使目标程序能够正常运行，复现仍可能因缺少必要的初始状态、无法到达漏洞代码或输入未满足触发条件而失败。此外，程序崩溃或异常响应也可能由其他缺陷引起，需要进一步确认实际执行行为是否与目标漏洞一致。因此，漏洞复现需要同时解决环境与状态准备、漏洞触发条件分析及安全影响验证等问题，难以依靠固定的测试流程完成。

4. **安全规约生成与形式化验证（Security Specification and Formal Verification）**

   形式化验证利用模型检查（Model Checking）、定理证明（Theorem Proving）等技术，检查程序是否满足预期的安全性质。这些技术能够在给定规约和环境假设下提供严格的验证结果，但通常要求研究者预先定义程序不变量（Invariants）、函数前置条件与后置条件，以及外部环境的行为假设。在实际软件中，相关信息可能分散在设计文档、API 使用约定及程序实现中，需要结合程序语义进行提取和形式化表达。例如，验证一个 API 的安全使用方式，需要明确其参数约束、调用顺序及操作之间的状态依赖；验证复杂组件时，还需要准确描述外部函数和运行环境的行为。规约的准确性直接影响验证结论，人工构造和维护这些规约通常需要大量专业知识与分析工作，限制了形式化验证的自动化应用。

5. **自动化漏洞修复（Automated Vulnerability Repair）**

   自动化漏洞修复旨在定位漏洞根因，生成能够消除安全缺陷的补丁，同时保持程序原有的功能与行为。传统自动程序修复（Automated Program Repair, APR）技术通常通过修复模板、程序搜索或约束求解生成候选补丁，再利用测试用例评估修复效果。然而，漏洞修复往往需要理解缺陷产生的原因及其与周围代码的关系。例如，访问控制漏洞可能涉及多个函数中的权限检查与状态更新，内存安全漏洞也可能需要调整跨函数的数据处理逻辑。此外，由于测试覆盖范围有限，候选补丁可能通过已有测试，却仍然保留其他可利用路径，甚至引入新的功能错误。这类补丁过拟合（Patch Overfitting）问题，使得准确定位漏洞根因、生成符合程序语义的补丁，以及充分验证修复效果成为自动化漏洞修复中的主要挑战。

6. **自动化渗透测试（Automated Penetration Testing）**

   渗透测试通过信息收集、漏洞利用、权限提升和横向移动等操作，评估目标系统的安全性。这类任务通常涉及多个主机、服务及相互依赖的攻击步骤，需要根据不断变化的目标环境选择后续操作。例如，攻击者可能需要先获得某台主机的访问权限，再利用获取的凭据访问内部服务，进而发现新的攻击入口。每一步操作都可能改变已有权限、网络可达性及后续攻击路径。传统自动化工具能够高效完成端口扫描、漏洞匹配及已知漏洞利用，但多阶段攻击通常依赖预定义的攻击规则和执行流程，难以覆盖复杂环境中不断变化的攻击条件。因此，如何持续维护目标环境与权限状态，并根据实际执行结果调整后续攻击步骤，是端到端自动化渗透测试面临的主要挑战。

7. **安全事件调查与运维处置（Security Investigation and Operational Remediation）**

   安全事件调查旨在从系统日志、网络流量和安全告警中识别恶意活动，分析事件之间的关联，并重建攻击过程。实际攻击通常涉及多个主机、进程及连续的系统操作，相关行为分散在大量审计数据中，还可能与正常业务活动混杂。传统基于特征匹配和异常检测的方法能够识别局部可疑行为，但完整的攻击过程重建仍需要关联不同时间和系统中的事件，并分析其因果关系。在安全运维阶段，漏洞处置、补丁部署和系统恢复还需要遵守维护窗口、服务可用性及变更审批等要求。由于不同操作之间存在状态依赖，单个操作满足执行约束，也不能保证后续操作能够顺利完成。这使得跨事件关联分析、攻击过程重建，以及满足运行约束的多步骤安全处置，成为安全事件调查与运维自动化中的重要问题。

## 3 Agentic System 的关键技术设计

上述任务虽然具有不同的研究目标，但在自动化过程中面临一些共同困难：程序分析需要确定应用特定的安全规则，动态测试需要满足复杂的输入与状态约束，而漏洞修复和渗透测试则需要根据执行结果调整后续操作。这些任务涉及代码理解、信息收集、工具执行和结果检查等多个环节，往往需要安全专家参与。

Agentic System 利用 LLM 分析代码、技术文档和运行反馈，并通过工具调用将分析结果转化为具体操作。借鉴 [SoK: DARPA's AI Cyber Challenge (AIxCC): Competition Design, Architectures, and Lessons Learned（USENIX Security 2026）](https://www.usenix.org/conference/usenixsecurity26/presentation/zhang-cen) 对自动化安全系统架构与技术设计的分析方式，本节从以下五个方面归纳相关工作的技术设计与贡献。

<a id="sok-d1"></a>

### 3.1 安全规则与规约的自动推断（Security Rule and Specification Inference）

程序安全分析与形式化验证通常需要预先定义检测规则或安全规约，但这些要求往往隐含在程序实现和技术文档中。例如，访问控制分析需要确定用户对特定资源的操作权限，API 安全分析需要明确参数及调用顺序约束，而形式化验证则需要给出程序应满足的安全性质。

LLM 能够结合程序代码、接口定义及相关文档推断这些应用特定的要求。相关工作进一步利用 Agent 收集和分析证据，生成可供静态分析、动态测试或形式化验证工具使用的规则，并通过工具反馈检查和修正生成结果。

例如，[BACAgent](https://lfysec.github.io/paper/bacagent-ccs26.pdf) 利用静态分析识别资源访问路径和已有权限检查，再由 Agent 结合业务代码、数据库结构及框架文档，推断接口应满足的访问控制策略，并与实际实现进行比较。[NEO](https://arxiv.org/abs/2605.15569) 提供跨语言、跨服务的代码分析能力，使 Agent 能够根据分析目标查找相关代码，判断特权操作是否缺少必要的权限检查。[MoCQ](https://peng-hui.github.io/data/paper/ccs26:mocq.pdf) 则从已有漏洞样例中提取检测模式，生成静态分析查询，并根据执行结果修正查询。

类似的设计也用于 API 安全分析和形式化验证。[GPTAid](https://www.ndss-symposium.org/wp-content/uploads/2025-465-paper.pdf) 从 API 实现中推断参数使用规则，通过构造遵守和违反候选规则的调用程序，检查规则是否符合实际行为。[PropertyGPT](https://www.ndss-symposium.org/wp-content/uploads/2025-1357-paper.pdf) 检索相似智能合约及其已有安全性质，为目标合约生成形式化规约，再利用验证工具检查生成结果。[SPAR](https://www.usenix.org/system/files/usenixsecurity26-ye.pdf) 同时生成协议格式规范与参考解析器，通过差分测试识别并修正两者的不一致。

这类工作的技术贡献在于**从代码和文档中推断安全要求，并将其转化为分析工具能够执行和检查的规则或规约**。其中，证据获取、规则生成和结果检查共同决定了自动化分析的有效性。

<a id="sok-d2"></a>

### 3.2 执行环境与前置状态的自动准备（Environment and State Preparation）

动态测试和漏洞复现通常要求目标程序处于特定的运行环境或程序状态。例如，测试 Web 应用中的某个功能可能需要先完成身份认证、创建业务对象等操作；固件服务可能依赖特定硬件接口；漏洞复现则需要恢复受影响的软件版本及其依赖配置。

这些准备步骤依赖具体的目标程序，所需操作及执行顺序也可能随运行结果而变化。Agent 可以根据任务目标和当前环境规划操作，调用浏览器、命令行或程序分析工具，并通过执行反馈判断是否需要补充或调整准备步骤。

例如，[YuraScanner](https://www.ndss-symposium.org/wp-content/uploads/2025-388-paper.pdf) 将 Web 应用探索组织为面向业务目标的多步骤交互任务。Agent 根据页面内容、任务目标及历史操作选择后续交互，再通过浏览器执行，使扫描器能够访问需要特定操作序列才能到达的业务功能。

在漏洞复现中，[CVE-Genie](https://sites.cs.ucsb.edu/~chris/research/doc/ccs26_cvegenie.pdf) 根据 CVE 描述、源码及相关文档分析漏洞的环境依赖，执行软件安装、依赖配置和环境检查，并利用执行日志处理构建过程中的问题。[Firmenstein](https://www.usenix.org/system/files/usenixsecurity26-wang-yanzhong.pdf) 则通过 API 依赖图识别阻碍固件运行的环境依赖，并生成相应的干预代码，帮助固件服务在仿真环境中继续执行。类似的准备需求也存在于形式化验证：[AutoSOUP](https://arxiv.org/abs/2605.10712) 协助生成验证环境与函数前置条件，并利用分析工具检查相关假设。

这类工作的技术设计主要围绕**前置条件分析、操作序列规划和执行状态检查**展开。Agent 根据目标程序的实际需求确定准备步骤，并利用执行结果调整操作，从而减少环境配置和状态准备中的人工工作。

<a id="sok-d3"></a>

### 3.3 基于程序语义的测试输入生成（Semantics-Guided Test Generation）

动态安全测试的另一项主要挑战是生成能够满足复杂输入约束，并到达目标程序路径的测试用例。传统模糊测试擅长大规模输入变异，但随机生成的输入往往无法满足复杂的数据格式、参数关系或 API 调用顺序。

LLM 能够通过分析程序代码和文档，提取输入约束及函数调用关系。相关工作将这些信息转化为测试入口程序（Harness）、输入生成器或测试约束，再交由传统测试工具批量生成和执行测试用例，使模型对程序语义的分析能够服务于多轮测试。

例如，[PromeFuzz](https://raw.githubusercontent.com/TCA-ISCAS/PromeFuzz-ccs-2025/master/paper/ccs25-full.pdf) 根据 API 的实现和使用方式生成测试 Harness；[SynapseFlow](https://arxiv.org/abs/2607.07007) 进一步分析函数间的数据流关系，将相关函数组织为测试单元，再通过分阶段生成与失败回退机制构造 Harness。[ELFuzz](https://www.usenix.org/system/files/usenixsecurity25-chen-chuyang.pdf)、[PDFuzzer](https://sites.cs.ucsb.edu/~chris/research/doc/ccs26_pdffuzz.pdf) 和 [Bulbasaur](https://www.usenix.org/system/files/usenixsecurity26-wang-yiyi.pdf) 则分别利用模型生成输入生成程序、API 调用约束和针对特定分支的变异器，将程序使用知识引入模糊测试。

部分工作进一步利用 Agent 分析漏洞触发条件。[PBFuzz](https://arxiv.org/abs/2512.04611) 根据目标漏洞代码和执行反馈，推断漏洞代码的可达性约束（Reachability Constraints）与触发约束（Triggering Constraints），并将其编码为参数化输入生成器，再利用基于性质的测试（Property-Based Testing）搜索具体输入。[GONDAR](https://arxiv.org/abs/2604.01645) 则通过探索 Agent 和利用 Agent 分别处理目标代码的可达性与漏洞触发问题：前者结合路径信息和覆盖率反馈寻找能够到达目标危险操作（Sink）的输入，后者根据 Sink 的语义进一步调整输入，以满足漏洞触发条件。

这些研究将**程序语义分析与测试输入生成、搜索相结合**，使传统测试工具能够利用模型推断的约束探索目标程序。PBFuzz 和 GONDAR 进一步区分了到达漏洞代码与实际触发漏洞所需的条件，为定向漏洞测试提供了更具体的指导。

<a id="sok-d4"></a>

### 3.4 基于执行反馈的任务规划与调整（Feedback-Guided Planning and Execution）

漏洞修复、渗透测试和复杂程序分析通常需要连续执行多个步骤，而后续操作又依赖此前的分析结果。例如，程序分析脚本可能执行失败，候选补丁可能无法通过测试，攻击操作也可能因目标环境变化而失效。因此，自动化系统需要根据执行反馈调整分析方案，并保留后续操作所需的信息。

Agentic System 可以将程序分析器、编译器和测试器等工具的输出用于后续决策，根据失败原因重新选择分析目标、修改操作参数或调整执行顺序。对于执行步骤较多的任务，相关研究还通过任务分解和状态管理，维护已有分析结果与执行进展。

例如，[BINREX](https://www.usenix.org/system/files/usenixsecurity26-liu-yuzhe.pdf) 通过语义检索定位与分析目标相关的二进制函数，再将复杂分析任务分解为多个子任务。Agent 根据子任务生成 IDAPython 脚本，并利用执行结果检查分析是否成功，逐步完成后续分析。[PatchAgent](https://www.usenix.org/system/files/usenixsecurity25-yu-zheng.pdf) 将漏洞定位、补丁生成和验证结合起来，通过语言服务器辅助代码分析，并根据编译和测试反馈持续调整候选补丁。[AhFuzz](https://abhikrc.com/pdf/NDSS27.pdf) 则根据运行时覆盖反馈，协调模糊测试与具体符号执行（Concolic Execution），动态调整后续测试安排。

对于多阶段渗透测试，[Incalmo](https://arxiv.org/abs/2501.16466) 将攻击规划表示为网络扫描、主机入侵等高层任务，再由专门的执行模块将其转化为具体工具命令。同时，系统通过独立的状态管理服务记录已发现的主机、凭据和攻击进展，为后续决策提供所需信息。

这些工作通过**任务分解、工具调用、执行反馈和状态管理**支持多步骤安全任务的自动执行。任务分解将复杂目标转化为可执行操作，反馈用于发现和修正错误，状态管理则使后续操作能够利用此前获得的信息。

<a id="sok-d5"></a>

### 3.5 基于外部工具的结果验证（Tool-Based Validation）

Agent 生成的安全规则、测试输入和修复方案还需要经过实际验证。例如，生成的 PoC 可能在到达目标漏洞前便触发其他异常，候选补丁也可能通过已有测试，却仍然存在漏洞绕过或功能回归。

为此，相关工作将编译器、测试器、程序分析器及专门的验证程序集成到执行流程中，通过实际运行检查 Agent 的输出，并利用验证反馈修正后续操作。不同安全任务需要采用与其目标相对应的成功判据。

例如，[CVE-Genie](https://sites.cs.ucsb.edu/~chris/research/doc/ccs26_cvegenie.pdf) 根据目标漏洞的安全影响构造相应的验证逻辑，检查生成的 PoC 是否触发目标漏洞。对于未授权删除漏洞，验证器可以先创建测试数据，再执行未授权删除请求，最后检查目标数据是否实际被删除。在补丁修复中，[SlicePatch](https://seclab.cse.cuhk.edu.hk/papers/sp26-SlicePatch.pdf) 利用定向差分模糊测试比较修复前后程序的行为，识别潜在的补丁绕过与功能回归，并根据测试反馈调整候选补丁。

在安全运维中，[PatchWeaver](https://www.usenix.org/system/files/usenixsecurity26-li-rui.pdf) 将变更管理要求表示为可执行策略，通过模拟候选操作对 Kubernetes 环境的影响，检查操作计划是否违反维护窗口、审批及服务可用性等约束。在安全事件调查中，[OCR-APT](https://arxiv.org/abs/2510.15188) 从审计日志中识别异常子图，再利用 LLM 分阶段关联攻击事件，并检查各阶段提取的证据，以支持攻击过程重建。

这些研究通过**外部执行与验证工具检查模型生成的结果，并将验证反馈用于后续修正**。验证的有效性取决于所检查的安全性质、执行条件及覆盖范围，因此需要根据具体任务明确成功判据。

### 小结

现有工作的技术设计主要体现出两种方式。一类利用 LLM 从程序代码、技术文档和运行信息中提取分析所需的知识，将其转化为安全规则、测试约束或可执行程序，再交由传统安全工具处理；另一类利用 Agent 根据工具执行结果调整分析方案，支持环境准备、漏洞复现及多步骤安全操作。实际系统通常结合多种设计，完成从任务分析、操作执行到结果验证的完整流程。各项设计对最终效果的贡献，还需要通过实验进一步区分。

<a id="sok-4"></a>

## 4 实验设计与有效性评估

前述研究通常将 LLM 与传统安全工具结合，通过规则推断、任务规划、工具调用及执行反馈完成安全任务。因此，实验既需要验证系统的端到端效果，也需要分析关键技术设计对最终结果的贡献。结合前述 [AIxCC SoK](https://www.usenix.org/conference/usenixsecurity26/presentation/zhang-cen) 对自动化安全系统评测条件的分析，相关研究主要从以下四个方面展开验证。

1. **端到端任务效果（End-to-End Effectiveness）。** 这类实验通常选择真实软件、公开漏洞或标准化测试环境，将提出的系统与现有自动化工具、通用 LLM Agent 或固定工作流方法进行比较。评价指标取决于任务目标，例如漏洞检测的准确率与召回率、动态测试的代码覆盖率与漏洞发现数量、漏洞复现的成功率，以及自动修复的补丁正确率。实验需要在明确的任务条件和成功判据下，评估系统完成实际安全任务的效果。

2. **关键技术设计的有效性（Ablation Study）。** Agentic System 通常包含多个组件，因此需要通过消融实验分析性能改进的来源。例如，[BACAgent](https://lfysec.github.io/paper/bacagent-ccs26.pdf) 比较了按需检索分析证据与一次性提供全部上下文的效果，以评估证据获取策略的作用。[PBFuzz](https://arxiv.org/abs/2512.04611) 则在相同基础模型下逐步引入执行反馈、程序分析工具及完整工作流，分析不同设计对漏洞触发成功率的影响。当一组实验同时增加多个组件时，所得结果只能反映其综合效果，需要进一步的独立对照确定各组件的贡献。

3. **分析结果的正确性（Result Validation）。** 安全任务需要与研究目标一致的成功判据。漏洞复现需要确认目标漏洞实际触发，补丁修复则需要检查漏洞是否消除，以及程序原有功能是否受到影响。相关研究通常结合人工核验、动态执行、Sanitizer 或专门的验证程序检查结果。[CVE-Genie](https://sites.cs.ucsb.edu/~chris/research/doc/ccs26_cvegenie.pdf) 根据漏洞类型构造相应的验证逻辑，检查预期的安全影响是否发生；[SlicePatch](https://seclab.cse.cuhk.edu.hk/papers/sp26-SlicePatch.pdf) 通过定向差分模糊测试检测补丁绕过与功能回归。对于漏洞复现，还应分别检查是否到达目标代码、是否触发目标漏洞，以及预期安全影响是否实际发生。

4. **泛化能力与执行成本（Generalizability and Efficiency）。** 为评估方法在不同条件下的适用性，部分工作进一步在不同软件项目、漏洞类型和基础模型上开展实验，并通过重复执行分析结果的稳定性。例如，[PrivEscalate](https://arxiv.org/abs/2609.09087) 的实验显示，相同规划机制在不同模型上的效果存在差异。此外，实验还需要统计模型调用次数、Token 消耗、工具执行时间及人工干预成本。不同系统之间的比较应说明输入信息、可用工具、执行预算和验证条件，以避免实验设置差异影响结论。

总体来看，现有研究主要通过**端到端对比实验评估任务完成效果，通过消融实验分析关键技术贡献，并结合独立验证、泛化测试和成本分析评估系统的实际可用性**。对于 Agentic System，控制基础模型、外部工具及执行预算等条件，有助于判断性能改进来自模型能力、系统设计还是两者的结合。

<a id="sok-5"></a>

## 5 技术贡献与发展方向

综合前文的技术分析，Agentic System 对传统安全技术的改进主要体现在两个方面。

首先，**利用 LLM 的代码理解与推理能力，自动获取安全分析所需的知识和约束。** 传统静态分析、模糊测试和形式化验证通常需要人工提供检测规则、测试约束或安全规约。相关工作通过分析程序代码、技术文档及运行信息，推断这些要求，并将其转化为安全规则、测试程序或验证条件，减少了人工编写和维护分析规则的工作。

其次，**通过工具调用和执行反馈，支持复杂安全任务中的多步骤执行与动态调整。** 在环境准备、漏洞复现、补丁修复和渗透测试等任务中，Agent 能够根据当前执行状态选择后续操作，并利用工具反馈修正失败的步骤。任务分解与状态管理进一步帮助系统处理操作之间的依赖关系，支持连续的安全分析与测试。

结合现有方法的局限，以下问题值得继续研究：

1. **安全规则与规约的正确性和完整性。** Agent 可以从程序实现中推断访问控制策略、API 使用约束等安全要求，但程序本身可能存在缺陷，生成结果也可能遗漏必要条件。如何结合设计文档、程序行为及独立测试，检查推断规则是否符合真实安全要求，是提高自动化分析可靠性的重要问题。

2. **复杂环境与程序状态的准备和验证。** 现有系统已经能够自动执行环境配置与多步骤交互，但具有复杂状态依赖的任务仍要求系统准确判断前置条件是否满足。例如，漏洞复现可能同时依赖特定用户权限、业务对象及服务配置。如何明确表示这些条件，并在执行过程中检查其满足情况，有助于减少因环境或状态准备不足导致的复现失败。

3. **漏洞触发与安全影响的准确验证。** 代码覆盖率、程序崩溃或异常响应通常不足以单独确认目标漏洞。后续研究可以进一步区分目标代码的可达性、漏洞触发和实际安全影响，并针对不同漏洞类型构造相应的验证条件。这有助于定位失败发生的环节，并为后续测试提供更准确的反馈。

4. **Agent 决策的可靠性与执行效率。** 频繁调用模型可能增加执行时间和成本，错误的分析结果也可能导致重复探索。如何确定哪些步骤需要 Agent 参与决策，以及何时可以直接使用现有分析工具，仍值得研究。同时，需要在相同模型、工具与执行预算下比较反馈驱动的动态规划和固定工作流，明确自主决策带来的实际收益。

总体而言，相关研究表明，LLM 能够协助推断安全分析所需的规则与约束，Agent 则进一步支持依据执行反馈调整操作。这些能力与传统分析、测试和验证工具相结合，为复杂安全任务的自动化提供了新的技术途径。后续研究需要继续提高生成规则的准确性、任务执行的可靠性以及验证结果的可信度，并通过严格的对照实验确认各项设计的实际贡献。
